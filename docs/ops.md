# Operations

How keep runs, is backed up and is restored. The decision behind it is
[ADR 0024](decisions/0024-rust-sqlite-per-org.md). The plan is
`factory/plans/migration-rust.sv`, step F2.

## Shape

One Fly app per environment, each with one machine and one volume, in
London (`lhr`):

| app | host | data | deploys |
|---|---|---|---|
| `keep-staging` | `staging.keep-together.org.uk` | reset to the riverside seed on every deploy | every push to `main` (`deploy.yml`) |
| `keep-prod` | `app.keep-together.org.uk` | real | by hand, from cutover (C2) |

The image (`rs/Dockerfile`) holds the api, the built SPA, Litestream and
a few scripts. The process tree inside the machine:

```
entrypoint.sh            restore an empty volume, reset staging, then exec
└─ litestream replicate  replicates /data/platform.db and /data/orgs/*.db to S3
   └─ api                serves /api, /healthz and the SPA on :8080
                         runs the hourly snapshot job
```

Litestream is PID 1 (after the entrypoint execs), so replication starts
before the api writes anything and gets the last WAL frames out after the
api exits. Fly sends SIGTERM, Litestream passes it to the api, and
`kill_timeout` gives both 30 s.

Data on the volume (`/data`):

| path | what |
|---|---|
| `platform.db` | tenants, users, memberships, sessions, the snapshot ledger |
| `orgs/<tenant-id>.db` | one organisation, named by its 32-hex tenant id |
| `premigrate/` | the `VACUUM INTO` copies taken before a boot migration (F1); `scripts/ops/rollback-migration.sh <data> [--apply]` puts them back |
| `snapshots-tmp/` | the snapshot job's scratch copies, removed after each file |
| `drill/` | the restore drill's write-loss probe, only during a drill |
| `.image` | the image the data belongs to (staging's reset compares it) |
| `.restored` | how the volume was last restored; reported until a human deletes it and restarts the machine |
| `restore.log` | the last empty-volume restore's output |

## Settings

Set in `fly.staging.toml` or the image: `KEEP_ENV`, `KEEP_DATA_DIR=/data`,
`KEEP_BIND=0.0.0.0`, `KEEP_PORT=8080`, `KEEP_STATIC_DIR=/app/dist`,
`KEEP_LITESTREAM_SOCKET=/run/litestream.sock`, `KEEP_RESET_SEED`
(staging only; refused when `KEEP_ENV=prod`), and auth's
`KEEP_APP_ORIGIN`, `KEEP_CLIENT_IP_HEADER=Fly-Client-IP` and `KEEP_MAIL`.
With `KEEP_ENV=staging|prod` the api won't boot without the origin, the
client-IP header and both auth keys, and refuses `KEEP_MAIL=log`
(`rs/crates/api/src/auth/boot.rs`).

Fly secrets:

| secret | from | used by |
|---|---|---|
| `LITESTREAM_BUCKET`, `LITESTREAM_ACCESS_KEY_ID`, `LITESTREAM_SECRET_ACCESS_KEY` | `scripts/aws/backup.sh <env>` | Litestream, `restore.sh litestream` |
| `KEEP_SNAPSHOT_BUCKET`, `KEEP_SNAPSHOT_ACCESS_KEY_ID`, `KEEP_SNAPSHOT_SECRET_ACCESS_KEY` | `scripts/aws/backup.sh <env>` | the snapshot job, `keep-snapshot` |
| `SENTRY_DSN` | Sentry project, EU region | api errors |
| `KEEP_SETTINGS_KEY`, `KEEP_AUTH_PEPPER` | generated by `scripts/fly/staging.sh` (32 random bytes each) | TOTP secrets are sealed under the first, codes are HMAC under the second. **Never replace `KEEP_SETTINGS_KEY` on a live app**: every enrolled authenticator app becomes unreadable (those users need a 2FA reset). A new pepper voids recovery codes and live emailed codes |
| `KEEP_SMTP_URL` | SES SMTP credentials (below) | auth mail, once `KEEP_MAIL=smtp` |
| `KEEP_RESTORE_SOURCE`, `RESTORE_DRILL` | set and unset by the drill | the entrypoint's restore |
| `KEEP_RESTORE_ALLOW_MISSING` | the human, after a restore stopped on missing orgs | the entrypoint's restore |

GitHub (repo settings): secret `FLY_API_TOKEN`; variables `STAGING_URL`,
`SENTRY_DSN_SPA` (built into the SPA; a DSN is public by design),
`LITESTREAM_BUCKET`, `SNAPSHOT_BUCKET`, later `PROD_URL`; secrets
`DRILL_LITESTREAM_KEY_ID/_SECRET` and `DRILL_SNAPSHOT_KEY_ID/_SECRET` for
`drill.yml`.

Locally none of this is needed: without `LITESTREAM_BUCKET` the
entrypoint runs the api alone, and without `KEEP_SNAPSHOT_BUCKET` there
are no snapshots. `KEEP_SNAPSHOT_BUCKET=file:///some/dir` uses a
directory as the bucket, for trying the restore path.

## First-time setup (the human runs these)

In order. Each script is idempotent and echoes every command.

1. `aws sso login --profile mgmt`, then `scripts/aws/bootstrap.sh`: adds
   the `keep-backup` account (it asks before creating it).
2. `scripts/aws/backup.sh staging`: both buckets, the IAM users, and the
   `fly secrets set` and `gh secret set` lines with the new keys.
3. `fly auth login`, then `scripts/fly/staging.sh`: the app, the volume,
   the secrets it still lacks, the certificate; it prints the Route 53
   record and the GitHub token commands.
4. Add the Route 53 record, run the printed `gh` commands, then deploy:
   `fly deploy -c fly.staging.toml --ha=false` or push to `main`.
   **Always `--ha=false`:** without it flyctl's first deploy makes two
   machines with two volumes, each replicating its own `platform.db` to
   the same prefix. `staging.sh` refuses to go on when the app has more
   than one machine or volume.
5. Run the restore drill (below) and paste its table into the log at the
   end of this page.

At cutover: `scripts/aws/backup.sh prod`, a `scripts/fly/prod.sh` (C2
writes it from `staging.sh`), and the prod path of `deploy.yml`.

### Mail on staging (later, human-run)

Staging runs `KEEP_MAIL=off` until SES is set up: whatever needs an email
is refused (reset links, admins' invites, emailed codes, admin 2FA
resets), so staging signs in with authenticator apps only. Invite links
come from the operator: `fly ssh console -a keep-staging`, then
`keep auth invite <slug> <email> --role …`, which prints the mail to that
terminal, never to the app's logs. A 2FA reset there is `keep auth
reset-2fa`, but the person then can't re-enrol (that needs an emailed
code) until mail is on. To turn mail on:

1. `scripts/aws/ses.sh`: in SES (`keep-mail-tx`, eu-west-2), verify
   `auth.keep-together.org.uk`, with Easy DKIM CNAMEs, a custom MAIL FROM
   (`bounce.auth…` MX and SPF TXT) and DMARC TXT on `_dmarc.auth…`, all
   written to keep-prod's Route 53 zone. Re-run it to see the status.
2. Request SES production access (out of the sandbox).
3. An IAM user limited to `ses:SendRawEmail` from
   `no-reply@auth.keep-together.org.uk`; derive its SMTP password.
4. `fly secrets set -a keep-staging --stage
   KEEP_SMTP_URL='smtp://USER:PASS@email-smtp.eu-west-2.amazonaws.com:587?tls=required'`,
   set `KEEP_MAIL = "smtp"` in `fly.staging.toml`, deploy, and send one
   test (a reset request for your own address): lettre's TLS against SES
   is untested so far.

## Backups

Two copies, independent of each other.

**Litestream** (continuous). Bucket `keep-litestream-<keep-prod
account>` in `keep-prod`, eu-west-2, versioned, SSE-S3, public access
blocked. Layout: `<prefix>/platform.db/…` and
`<prefix>/orgs/<tenant-id>.db/…`. The prefix is `prod` for prod. Staging
gets `staging/<deployment>` because its reset recreates every file on
each deploy, and a fresh file must not meet the previous one's replica.
It syncs every second, takes a full snapshot daily and keeps 7 days, so
any point in the last week can be restored. Old object versions expire
after 30 days. The IAM user `keep-litestream-<env>` can read, write and
delete under its env's prefix only. Litestream needs delete for its own
retention.

Staging's old per-deploy prefixes stay until pruned. No lifecycle rule
expires them, because one would also delete the live generation's files
whenever staging goes 14 days without a deploy. They are small. To prune
all but the newest few (as an admin of keep-prod):

```
b=keep-litestream-<keep-prod account>
aws s3api list-objects-v2 --profile keep-prod --bucket $b --prefix staging/ --delimiter / \
  --query 'CommonPrefixes[].Prefix' --output text | tr '\t' '\n' | sort | head -n -3 |
  while read -r p; do aws s3 rm --profile keep-prod --recursive "s3://$b/$p"; done
```

**Hourly snapshots.** Bucket `keep-snapshots-<keep-backup account>` in
the `keep-backup` account, which runs nothing else, with Object Lock
(governance, 2 days). The job is `api::backup`. A minute after boot and
then every hour, it copies `platform.db` and then each org file whose
newest revision moved since its last snapshot, with `VACUUM INTO`.
`orgs/` is listed after the platform copy, so that copy never names an
org the run didn't see. It checks the copy with `integrity_check`,
compresses it with zstd and uploads it to
`<tier>/<env>/<tenant-id|platform>/<YYYY-MM-DDTHHMMZ>.db.zst`:

- `hourly/` when the file changed in the last hour; expires after 2 days;
- `daily/` at the first run of a UTC day, when it changed since the last
  daily; expires after 30 days;
- `monthly/` at the first run of a UTC month, whether it changed or not;
  expires after 365 days.

The newest state of every file is always in the bucket: hourly for two
days, then daily, then monthly.

**Nothing the app holds can remove or replace a snapshot.**
- Every upload is create-only (`If-None-Match: *`). The bucket policy
  refuses a PUT from a `keep-snapshots-*` user without that header, so a
  stolen app key can add junk keys but can't overwrite a real one. A key
  that already exists (two passes in one minute) is skipped and stays
  due.
- The IAM user `keep-snapshots-<env>` can put, get and list under its
  env's prefixes. Both its policy and the bucket policy deny delete,
  retention changes, legal holds, governance bypass, and bucket policy
  or lifecycle changes.
- Each tier's lifecycle expiry leaves a noncurrent version, which goes a
  day later, so retention stays at 48 h, 30 days and 12 months. No
  other noncurrent versions arise, since the app can't overwrite.
- A restore ignores keys stamped in the future and falls back past a
  copy that fails its check, so planted junk can't block one.

Nobody who owns `keep-prod` can reach the bucket either.

The ledger of what was uploaded is the `snapshots` table in
`platform.db`. Fly's daily volume snapshots are a third copy we don't
rely on.

`keep-snapshot run --data /data` runs one pass by hand, beside the
running api.

### WAL checkpoints and Litestream

The api never checkpoints inside a commit. Org writers run with
`wal_autocheckpoint=0`: SQLite's default ran the checkpoint (copy the WAL
back, two fsyncs) inside whichever request's COMMIT crossed 1000 pages,
under the org's writer mutex, and that stalled writes by 100–500 ms under
disk load. Who checkpoints instead depends on Litestream.

**Without Litestream** (local, QC, anything without
`KEEP_LITESTREAM_SOCKET`), each open org file has a checkpointer thread
with its own connection (`rs/crates/store/src/checkpoint.rs`):

- a `PASSIVE` checkpoint about every second while anything has committed
  since the last one, and at once when a commit leaves 1000 or more pages
  (~4 MB) un-checkpointed;
- a `TRUNCATE` with no busy timeout when the file is idle and its `-wal`
  is over 4 MB: it shrinks the file, or gives up at once if anything holds
  a lock;
- closing a handle (LRU, idle-close) still checkpoints: SQLite does that
  on the last close whatever `wal_autocheckpoint` says.

**Under Litestream** (the image: `KEEP_LITESTREAM_SOCKET` is set) there is
no checkpointer thread, and Litestream does every checkpoint, as its docs
recommend. It holds a read lock on each database between syncs, which
stops any other process copying the WAL back: measured, all 176 of the
api's `PASSIVE` checkpoints in one run copied 0 pages. Litestream checkpoints
(`PASSIVE`, past `min-checkpoint-page-count`, 1000 pages) under its own
write lock, and writers wait for it. That hold is 150–250 ms at 400–2000
pages: mostly fixed cost inside Litestream (this disk's fsync is ~4 ms),
not size. The first checkpoint after a bulk import (~14k pages) holds
0.75–1.1 s.

Connections wait for a lock by polling every millisecond (up to 5 s), not
with SQLite's busy timeout, whose sleeps (1, 2, 5, … 100 ms) made a writer
oversleep Litestream's lock: waits came in at 53, 178, 228 and 328 ms,
the sleeps' running totals.

`platform.db` keeps SQLite's auto-checkpoint: it takes a handful of small
writes (sign-ins, memberships, session touches), not a request stream.

#### Measured (2026-10-24)

Litestream 0.5.17 (from the image) on this laptop's nvme with a file
replica, the api's org of 10k contacts, `scripts/perf-stall/bench.mjs`
with two writers. Server time per write, after the first 5 s (which hold
the seed's checkpoint):

| writes/s | build | Litestream | p99 ms | max ms | >150 ms |
|---|---|---|---|---|---|
| ~8 | old (main) | defaults | 3.3, 10.3 | 184, 71 | 2, 0 |
| ~8 | new | defaults | 3.1, 3.2, 3.3 | 27, 31, 46 | 0, 0, 0 |
| ~8 + cold `cargo build` | old | defaults | 10.4, 82.7 | 123, 190 | 0, 4 |
| ~8 + cold `cargo build` | new | defaults | 104.5, 30.9 | 187, 147 | 4, 0 |
| ~80 (whole run) | new | defaults | 140, 130 | 236, 754 | 30, 30 |
| ~80 (whole run) | new | `min-checkpoint-page-count: 10000` | 63, 15 | 1014, 1041 | 14, 14 |

Restores matched the live file row for row in every run.

`rs/litestream.yml` keeps Litestream's checkpoint defaults:

- `min-checkpoint-page-count` higher (10000) makes checkpoints rarer but
  each one longer (~1 s at 10k pages), lets the WAL reach ~40 MB per busy
  org, and with `synchronous=NORMAL` (the WAL is fsynced only at a
  checkpoint) widens the window in which a power loss or kernel crash, not
  a process crash, loses local commits that Litestream had already
  shipped. No gain at realistic rates.
- `monitor-interval: 250ms` with `min-checkpoint-page-count: 250` (smaller,
  more frequent checkpoints): same 150–250 ms per hold, four times as often.
- `checkpoint-interval` fires only when the WAL hasn't changed for that
  long (an idle file), so it doesn't touch write latency.
- `truncate-page-n` (~500 MB) is an emergency stop; left alone.

What remains: at sustained write rates far above a small charity's
(~80/s), every Litestream checkpoint stalls writes 150–250 ms; and after
a bulk import, its first checkpoint stalls them up to ~1 s. Under a
loaded disk either build sees a few writes over 150 ms.

`/healthz` reports `walBacklogBytes`, the WAL not yet checkpointed in the
worst open org file: under a few MB without Litestream; with it, the WAL's
length at the last commit since Litestream's last checkpoint. The
`wal-watch` job warns (log and Sentry) once when it passes 64 MB: a
checkpointer stuck, or a long read (a snapshot's `VACUUM INTO`) pinning
the WAL.

## Restoring

**A lost machine or volume** restores itself. When a machine boots on a
volume without `platform.db` and a backup is configured, the entrypoint
runs `restore.sh` into `/data/restoring`. The files move into place only
when every one is back and passed `integrity_check`. Then Litestream
starts as usual.

```
fly volumes create keep_data -a keep-staging --region lhr --size 1
fly deploy -c fly.staging.toml --image <current image> --ha=false
fly logs -a keep-staging | grep -E 'entrypoint|restore:'
```

What the entrypoint does, by case:
- **Litestream has the data:** it restores from Litestream.
- **Litestream has no replica at all** (exit 3): it falls back to the
  snapshots. Up to an hour of writes may be gone, so the fallback is
  loud: a `FALLBACK` log line, a Sentry error at every boot, and
  `backup.restore` in `/healthz`, which `health.yml` turns into an
  issue. All of these last until you check the data, delete
  `/data/.restored`, and restart the machine (the api reads the file at
  boot). Staging never falls back: its fresh per-deploy
  prefix is always empty, and its snapshots belong to the previous
  deploy.
- **Orgs that `platform.db` lists have no backup** (exit 4, e.g. an org
  created in the last second, or an upload that failed): the machine
  doesn't start. The log names the orgs (`MISSING org <id>`). To boot
  without them, set `KEEP_RESTORE_ALLOW_MISSING=1` and deploy again; the
  restore is then recorded as needing review. Unset it afterwards.
- **A source exists but fails** (bad credentials, a corrupt file): the
  machine doesn't start. Starting empty would replicate an empty
  `platform.db` over the real one.

Set the secret `KEEP_RESTORE_SOURCE=snapshot` before the deploy to
restore from the snapshots on purpose, and unset it after.

Follow-up (not built): `keep-snapshot restore --before <stamp>`, to take
the newest copies older than a given time. That would allow rolling back
past a bad import or an app bug, or past a tampered copy a compromised
app added (it can add a key, never replace one). Until it exists, pick an
older copy by hand (below).

**Point in time** (an app bug or a bad import, data still there). Restore
next to the live data, look, then swap by hand. Inside the machine:

```
export AWS_ACCESS_KEY_ID=$LITESTREAM_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY=$LITESTREAM_SECRET_ACCESS_KEY
prefix=prod   # staging: staging/<deployment>, the tag part of FLY_IMAGE_REF
litestream restore -timestamp 2026-10-24T09:00:00Z -o /data/pit/<id>.db \
  s3://$LITESTREAM_BUCKET/$prefix/orgs/<id>.db
sqlite3 -readonly /data/pit/<id>.db 'PRAGMA integrity_check'
```

To put one org back: stop the machine, replace `orgs/<id>.db` (and
delete its `-wal`/`-shm`), start it. The file carries its tenant id, so
it only opens under its own name. A snapshot works the same way:
download `<tier>/<env>/<id>/<stamp>.db.zst` with the AWS CLI and
`zstd -d` it.

**Everything, anywhere** (no Fly). `scripts/ops/restore.sh litestream
<dir>` or `restore.sh snapshot <dir>` with the same environment variables
restores into any empty directory, which `api` can then serve. That's
what `drill.yml` does each month on a GitHub runner.

## Restore drill

`scripts/ops/restore-drill.sh [litestream|snapshot|both]`, run by the
human against `keep-staging`. It:

1. seeds a 10k org (`drill`, the perf generator's people, through the
   `seed` bin) and takes a snapshot pass;
2. records counts with `drill.sh census`: tenants, and per org contacts,
   revisions and the matches of five search terms;
3. per source, destroys the machine and its volume, creates an empty
   volume and redeploys the same image, so the entrypoint restores. For
   Litestream it first sets the machine to `--restart no` (an update that
   restarts it), starts a loop committing one row at a time to
   `drill/marks.db`, then crashes the machine with `drill.sh hard-stop`.
   That prints the kill time, SIGKILLs Litestream, the api and the loop
   together, and deletes the data if the VM is still up. Neither a
   graceful flush nor a restart ships anything that wasn't replicated;
4. waits for `/healthz`, reads `restore: all files Ns` from the logs,
   recounts and diffs. The loss is the kill time minus the newest
   restored mark, both by the machine's clock: an upper bound on the
   window of committed writes lost;
5. prints the table below and exits 1 if anything misses. On any exit it
   unsets the secrets it set (`KEEP_RESTORE_SOURCE`, `RESTORE_DRILL`)
   and puts back the restart policy of a machine it changed that still
   exists.

**Pass:** a 10k org back in under 60 s from either source, counts and
search matches equal, and at most 1 s of committed writes lost on
Litestream. Snapshots lose up to an hour by design.

`drill.yml` repeats the restore part monthly (the 1st, 06:00 UTC) for
**staging only**, with read-only keys that can only read staging. It
restores from both sources on a runner, and fails if a file fails
`integrity_check`, if either source takes 60 s or more, if an org is
missing, or if the two sources list different tenants. The timings go
in the run summary.

**Prod is never restored on GitHub** (human, 2026-10-24). GitHub's
runners are probably outside the UK, and their logs are public if the
repo is. Neither the drill key nor `drill.yml` can read prod. The prod
drill is restore-only, run occasionally by the human on their own
machine or a UK box, with their own AWS profiles:

```
aws sso login --profile mgmt
scripts/ops/restore-drill.sh local prod          # add --keep to keep the files
```

It restores from Litestream and from the snapshots into a private
temporary directory, and checks every file. It prints only pass/fail,
timings, file and contact totals, and whether both sources list the same
tenants: no org names or ids. Then it deletes the restored data. It
needs the aws CLI, litestream 0.5.x and sqlite3, and builds
`keep-snapshot` from `rs/`. Paste its lines into the drill log.

## Monitoring

- `/healthz` (Fly's check every 15 s, and the cron): 200 when
  `platform.db` answers. Its `backup` field has:
  - `snapshotAgeSeconds`: of the last `platform.db` snapshot, which every
    run takes;
  - `snapshotErrorCount`: from this process's last run;
  - `litestream`: `ok`, `error` or `off`, or `starting` in the first two
    minutes while databases haven't synced yet;
  - `litestreamLagSeconds`: the worst database's seconds since its last
    sync, from the control socket's `GET /list`;
  - `litestreamDatabases`;
  - `restore`: present after an empty-volume restore, as `{source,
    fallback, missingOrgs, at}`.

  And `walBacklogBytes` at the top level: the worst open org file's WAL
  not yet checkpointed ("WAL checkpoints and Litestream" above).

  It is public, so it has counts and status words only. Error text
  (bucket names, account ids, tenant ids) goes to the log and Sentry, and
  a lasting Litestream problem is logged once, not every 15 s. A stale
  backup doesn't fail the Fly check: that would take the only machine
  out of service.
- `health.yml` every 15 minutes, for each URL in `STAGING_URL` and
  `PROD_URL`: fails on a non-200, a snapshot older than 2 h or never
  taken, snapshot errors, Litestream not `ok`, a lag over
  `LITESTREAM_MAX_LAG` (default 300 s), or a restore that fell back or
  left orgs out. A failure opens an issue labelled `health`, or comments
  on the open one. GitHub emails it.
- Sentry, EU region. The api reports panics and logged errors
  (`SENTRY_DSN`). The SPA imports `@sentry/browser` (npm, pinned) as a
  separate chunk, only when the build had `VITE_SENTRY_DSN`. It contacts
  Sentry only when there's an error to send. Both turn off user, cookie,
  header, body and query-string collection, scrub what's left, and
  redact anything shaped like an email address.
- Litestream's Prometheus metrics on :9090, scraped by Fly (`[metrics]`).

## Staging reset

`KEEP_RESET_SEED=riverside`: on the first boot of a new image (the
image ref differs from `/data/.image`) the entrypoint wipes `/data`
before Litestream starts, and the api seeds the `riverside` org. Restarts
and restored volumes keep their data. The seed is `seed::riverside`
(Convex's `testSeed`): 100 donors with notes, relationships,
identifiers, field values, acquisition codes, gifts and Gift Aid
declarations, and one user per role
(`admin@`, `staff@`, `viewer@keep-together.example`), each signing in
with a password and TOTP. Their credentials are the six Fly secrets
`KEEP_RIVERSIDE_<ADMIN|STAFF|VIEWER>_<PASSWORD|TOTP>`
(`scripts/fly/staging.sh` makes missing ones and prints them once); the
boot stops naming any that is missing, and they never reach the log. The
TOTP secrets survive the reset, so an authenticator app keeps working
across deploys. Locally, `KEEP_ENV=dev keep dev seed-riverside` makes the
same world and prints generated sign-ins.

`KEEP_QC_TOKEN` (a Fly secret, also made by `scripts/fly/staging.sh`)
opens `/api/qc/*` on staging for the nightly `pnpm qc --target staging`:
it seeds and signs into `qc-` groups only, never riverside. The api
refuses to boot with it under `KEEP_ENV=prod`.

## Preview (tailnet)

The house server runs `main` all the time with the riverside sample
data, reachable from the human's tailnet (phone included). It replaces
the old Convex `preview` deployment. Scripts in `scripts/preview/`:

| script | |
|---|---|
| `install.sh [--origin URL] [--port N]` | once, re-runnable: makes `~/.local/share/keep-preview/` (`KEEP_PREVIEW_HOME`) with its own https clone of the repo in `src/` (never a working checkout or a factory worktree), `preview.env`, `secrets.env`, the `systemd --user` units, the first build; prints the human's steps |
| `update.sh [--force]` | what `keep-preview-update.timer` runs every 5 min: deploy `origin/main` if it moved |
| `status.sh` | running commit, last update and its result, URL, health, the riverside sign-in emails and where their secrets are |

The installed copies live in `~/.local/share/keep-preview/bin/`; each
deploy replaces them with the new release's.

**What runs.** `keep-preview.service`: the release `api` of the commit in
`current/` (a symlink into `releases/<sha>/`, the last 3 kept), serving
the SPA from `current/dist` (`KEEP_STATIC_DIR`), bound to
`127.0.0.1:8780`, data in `data/`. `KEEP_ENV=dev`, `KEEP_MAIL=log`
(sign-in codes and reset links go to the journal), `KEEP_APP_ORIGIN` the
tailnet URL (`https://<host>.<tailnet>.ts.net`). `tailscale serve`
terminates TLS on the tailnet and proxies to the loopback port.

**Auth is real.** `KEEP_DEV_AUTH` is not set, so there is no dev login at
all; and even if it were, `/api/dev/*` is refused for any request whose
`Host` isn't loopback, which through `tailscale serve` it never is (the
ts.net name). Everyone signs in with a password and TOTP. `KEEP_ENV=dev`
is allowed only because the bind is loopback; the api refuses it (and
`KEEP_MAIL=log`) on any reachable bind. The auth keys and the three
riverside sign-ins (`admin@`, `staff@`, `viewer@keep-together.example`,
`KEEP_RIVERSIDE_<ROLE>_{PASSWORD,TOTP}`) are made once by `install.sh`
into `secrets.env` (0600) and never printed or logged: add the TOTP
secret (base32) to an authenticator app by hand. Rate limits see every
tailnet client as `127.0.0.1` (no `KEEP_CLIENT_IP_HEADER`: `tailscale
serve` passes the client address in `X-Forwarded-For`, which the api
refuses as a client-address header); fine for a household.

**Updates.** Every 5 min `update.sh` fetches `origin/main`; if it moved,
it builds in `src/` (`cargo build --release -p api`, `pnpm install`,
`pnpm build` with `VITE_BACKEND=rust`) at nice 19 / ionice idle with half
the cores, then stops the api, moves `data/` to `data.prev/`, points
`current` at the new release and starts it: the api seeds riverside at
boot (`KEEP_RESET_SEED`) with the same sign-ins, so an authenticator
keeps working. Changes made in the preview last until the next deploy.
It skips a run while another update holds `update.lock`, or while a QC
run holds `.qc.lock` in the main checkout (a build would skew QC's
timings). A failed build leaves the running release alone and is logged;
that commit isn't retried until `main` moves (or `update.sh --force`). A
release that doesn't answer `/healthz` within 2 min is rolled back to the
previous release and data.

Logs: `journalctl --user -u keep-preview` (the api) and
`journalctl --user -u keep-preview-update` (builds).

**One-time human steps** (`install.sh` prints them; it doesn't run them):

```bash
sudo loginctl enable-linger $USER     # user services survive logout and reboot
tailscale serve --bg --https=443 http://127.0.0.1:8780
# needs operator rights on some setups: sudo tailscale set --operator=$USER, once
```

With another `--https=<n>`, install with `--origin https://<host>.<tailnet>.ts.net:<n>`.
To remove it: `systemctl --user disable --now keep-preview.service
keep-preview-update.timer`, `tailscale serve --https=443 off`, then delete
`~/.local/share/keep-preview` and the three units in
`~/.config/systemd/user/`.

## Nightly QC

The C1 gate needs three nightly QC runs in a row against staging
(`factory/plans/migration-rust.sv`). They run on the house server, not
GitHub Actions: it's in the UK like the users (13 ms to staging; a GitHub
runner is ~80 ms away and would blow the budgets), and QC history is
local. Scripts in `scripts/qc-nightly/`:

| script | |
|---|---|
| `install.sh [--token-stdin]` | once, re-runnable: makes `~/.local/share/keep-qc-nightly/` (`KEEP_QC_NIGHTLY_HOME`) with its own https clone in `src/` (never a working checkout or a factory worktree), its `node_modules` and Playwright's chromium, `nightly.env`, `qc-token` (0600), the `systemd --user` units `keep-qc-nightly.{service,timer}`; enables the timer and checks gh works from a unit. Re-run it to install changed scripts |
| `run.sh` | one run: what the timer starts daily at 03:00 local (`Persistent=true`: a night the machine was off runs at the next boot) |
| `status.sh [N]` | the last N runs, the current streak of passing nights in a row (what the gate counts) with the commit each ran, the next run, the open issue |

**The token.** `pnpm qc --target staging` needs `KEEP_QC_TOKEN` (see
Staging reset). `install.sh` fetches a missing one with `fly ssh console
-a keep-staging -C 'printenv KEEP_QC_TOKEN'` straight into `qc-token`, or
takes it with `--token-stdin`; it is never printed. `run.sh` reads it into
the env of the `pnpm qc` process only: not argv, not the log, not any
other command. When the Fly secret changes, delete `qc-token` and rerun
`install.sh` (or pass the new one with `--token-stdin`).

**A run** (`run.sh`; one at a time, under `run.lock`: a second one
records `void reason=another-run`):

1. Waits up to 5 min for the network (DNS for staging, `gh api`). A
   night missed while the machine was off runs at the next boot, maybe
   before the network is up, and a `--user` unit can't order against
   `network-online.target`. Still no DNS: `void reason=no-network`. DNS
   but `gh` failing (an expired token, a lost keyring): `error step=gh`.
2. Waits up to 45 min for a Deploy workflow still queued or running
   (still busy: `void reason=deploy-busy`), then takes the commit staging
   runs: of the completed Deploy runs, the one that finished last
   (`updatedAt`, so a re-run of an old run counts when it ran) and got as
   far as its "Deploy keep-staging" step (`gh run list` / `gh run view`).
   That step succeeded: its commit. It failed or was cancelled part-way:
   staging could be on either image, `void reason=commit-uncertain`. Not
   `origin/main`: a push may still be deploying, or have failed CI and
   never reached staging. A deploy whose smoke test failed after `flyctl
   deploy` still counts, since staging serves that image. A `fly deploy`
   by hand bypasses all this, and the run would test the wrong commit.
3. Checks that commit out in `src/`, `pnpm install --frozen-lockfile`,
   `playwright install chromium` (a no-op unless Playwright moved).
4. Takes the preview's `update.lock` (waiting out a build already under
   way, up to 1 h), then the main checkout's `.qc.lock` (the
   `scripts/lockfile.mjs` format, so a local `pnpm qc` waits for it and it
   waits for a local run; the preview's updater skips while it's held).
5. Looks again: a deploy started, or another Deploy run finished (of
   any commit, the same one included: every deploy reseeds), during the
   waits: back to 2 (twice at most, else `void reason=staging-kept-changing`). Then
   re-dates `.qc.lock`, so the waits never make it look stale (2 h).
6. `pnpm qc --target staging`, then `pnpm qc:report`
   (`src/qc-report/trend.html`; history in `src/qc-results/history.jsonl`,
   staging lines only).
7. Looks again, comparing the Deploy run and its `updatedAt`, not just
   the commit: a deploy job started, or another Deploy run finished,
   during the run: `void reason=staging-changed-during-run` (every deploy
   reseeds, so neither a pass nor a fail means much). gh gets 3 tries;
   still unanswered, a pass becomes `void reason=staging-check-unknown`
   and a fail stays `fail` with `staging-check=unknown` (a loud false fail
   beats a quiet one).
8. Appends one line to `runs.log`: time, `commit`, `result`, and for a
   run that got to QC `flows` timed, flows `over` budget, median `rtt`,
   `rttover` (flows with a worker over the 150 ms RTT ceiling, whose
   latency the reporter didn't judge), `retries` (set-up calls sent again
   after no answer: passing, but `status.sh` flags them and the run's
   SETUP RETRIES banner says which, and whether the run before retried
   the same route), `exit` (QC's, when not 0); `step=` on an error,
   `reason=` on a void.

Results:

| result | means | alert |
|---|---|---|
| `pass` | QC passed against one deploy, latency judged | none |
| `fail` | QC failed: a test, a budget, a gate (also with `staging-check=unknown`) | issue |
| `error` | the run broke before QC could judge (`step=`: install, token, gh …) | issue |
| `void` | can't be trusted either way (`reason=` above; also `rtt-over-ceiling` on an otherwise passing run) | issue only when lasting |

A fail or error opens a GitHub issue labelled `qc-nightly` (GitHub emails
it), or comments on the open one, and the unit fails (exit 1); closing the
issue is by hand. A single void doesn't: a deploy at 03:00 is no fault.
Voids that last do, the same way: the last 2 runs both void, or 36 h
with no pass, fail or error. Some reasons persist (a failed `flyctl
deploy` with no push after it, a stuck Deploy run, staging's `/api/me`
over the RTT ceiling because the app is slow, not the link) and would
stall the gate unnoticed.

**The streak** (`status.sh`, what the gate counts):
passing nights in a row. Nights run noon to noon, so a hand run at 23:30
and the 03:00 run after it are one night. Any run that isn't a pass ends
the streak, a void too: that night wasn't tested, though it's no
failure. So does a night with no run. The gate wants three. Full output:
`~/.local/share/keep-qc-nightly/logs/` (last 30) and `journalctl --user
-u keep-qc-nightly`.

**First run** (after `install.sh`; linger is already on):

```bash
systemctl --user start --no-block keep-qc-nightly.service
journalctl --user -fu keep-qc-nightly.service
~/.local/share/keep-qc-nightly/bin/status.sh
```

`run.sh` uses gh from a unit with no login session: if `install.sh` says
`gh auth status` fails there, gh's token is in a desktop keyring; store
it in a file (`gh auth login --insecure-storage`). To remove it:
`systemctl --user disable --now keep-qc-nightly.timer`, then delete
`~/.local/share/keep-qc-nightly` and the two units in
`~/.config/systemd/user/`.

## To verify on the first real run

Checked locally (podman, 2026-10-24, file replicas instead of S3): the
image builds; Litestream 0.5.17 accepts `rs/litestream.yml` (socket,
snapshot keys, `dir` + `watch` beside a `path`, `${VAR}` expansion) and

Still to verify on the first real run (no AWS or Fly from the builder's
sandbox):

- Litestream against S3 with the IAM user limited to its prefix, and
  that `restore -if-replica-exists` with that user reports a missing
  replica (exit 3) rather than mistaking an access error for one.

  `If-None-Match` is refused (403), and one with it succeeds. Try it
  once with the new key:
  `aws s3api put-object --bucket <b> --key hourly/staging/test/x --body /dev/null`
  should fail, and the same with `--if-none-match '*'` should succeed.
